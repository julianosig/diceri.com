# Make the schema enforce what the code assumes

*Research report, 2026-11-25. Notes: [`notes/`](notes/). Rules adopted from it live in
[`AGENTS.md`](../../../AGENTS.md) §14 and [ADR 0010](../../decisions/0010-uuidv7-ids-and-database-conventions.md).*

Diceri should adopt **UUIDv7 as the internal primary and foreign key for every table**, generated in the application and stored as a 16-byte `BLOB` in `STRICT` SQLite tables (native `uuid` in PostgreSQL later), while keeping **everything that grants access out of that id space**: room share links stay 22-character base62 codes with 128 CSPRNG bits, and host and account keys stay 128-bit random secrets stored only as SHA-256. RFC 9562 is explicit that UUIDs "MUST NOT be used as security capabilities", and with the `uuid` crate only about 32 bits of a v7 id are fresh randomness when ids are minted in the same millisecond, so a v7 room link would be a real regression from today's 128 bits. Around the ids, the research converges on a small set of habits that make SQLite safe in production and keep the path to PostgreSQL short: the database is the last line of defense (NOT NULL by default, CHECK for every single-row invariant, named constraints, foreign keys with explicit `ON DELETE` and an index), instants are UTC integers in milliseconds, schema changes are versioned forward-only `sqlx::migrate!()` files instead of the startup `CREATE TABLE IF NOT EXISTS` string, connection pragmas are set explicitly in one place, and backups are continuous and restore-tested. In the hexagonal layout, sqlx never crosses into `application`; contract tests run one suite against both the in-memory fake and the SQLite adapter. Privacy law (GDPR and Brazil's LGPD) turns retention into a schema property: every table holding personal data needs a documented purpose, retention period and deletion path, and audio, transcripts and voice embeddings never get a column. Two concrete project changes fall out: the `domain` crate's dependency allow-list must grow to include `uuid` (an ADR-worthy change), and sqlx needs its `migrate` feature turned on before the second durable table lands.

## Three kinds of 128-bit values, and only one of them is a UUIDv7

The core design decision is to separate **identifiers** (handles that name a row), **capabilities** (values whose possession grants access) and **secrets** (values that prove identity). UUIDv7 serves only the first. Its layout is a 48-bit big-endian Unix-millisecond timestamp, 4 version bits, 2 variant bits and **74 bits that are random or partly a counter** ([RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html)). The RFC's security section says implementations should not assume UUIDs are hard to guess, that they "MUST NOT be used as security capabilities", and that v4 is the right choice if a UUID is used in a security operation ([RFC 9562 §8](https://www.rfc-editor.org/rfc/rfc9562.html)). The `uuid` crate makes the gap concrete: its shared `ContextV7` is a 42-bit counter reseeded each millisecond with a random 41-bit value, and `new_v7` keeps the counter in the high bits and fills the rest randomly ([docs.rs ContextV7](https://docs.rs/uuid/latest/uuid/timestamp/context/struct.ContextV7.html); [docs.rs uuid](https://docs.rs/uuid/latest/uuid/struct.Uuid.html)). Subtracting the 42-bit counter from the 74 available bits leaves **roughly 32 fresh random bits per id** once an attacker has seen a neighbouring id; that figure is derived from the crate docs, not stated by them. A v7 id also leaks its creation time, and ordering and rate information can sometimes be inferred from sequences of them ([Clockworks security notes](https://dexcompiler.github.io/Clockworks/concepts/security.html)). Shifting timestamps with `with_adjust_by_millis` hides the time but adds no entropy.

Diceri's room link is a capability in the strict sense. Under [ADR 0008](../../decisions/0008-named-rooms-and-live-board.md), a room with `entry = open` admits anyone who knocks, so for an unlisted open room the link alone is the key to the conversation. The room therefore needs two values: `id` (v7, the primary key every foreign key references) and a share code (today's `RoomId`, 128 CSPRNG bits as 22 base62 characters, `UNIQUE`). Re-encoding a v7 as base62 or Crockford base32 would make it look opaque while still carrying the timestamp and the low entropy, so it buys encoding complexity and nothing else. One question the notes leave open is whether the share code itself should be stored hashed, like host keys. The position this report takes is **no**: the server must re-display the link (on the live board for listed rooms, and to a host who reconnects), rooms are ephemeral, and a hashed code could not be shown again. The share code is protected instead by file permissions, short retention and never being logged. If a future flow makes a link one-time or never re-displayable, hash it.

Secrets stay exactly as [ADR 0009](../../decisions/0009-username-only-accounts.md) defines them. OWASP's password guidance (Argon2id at m=19 MiB, t=2, p=1 or stronger) targets human-chosen passwords and explicitly treats fast hashes as unsuitable for them ([OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)), but a 128-bit server-generated key cannot be dictionary-attacked, and practitioners consistently use SHA-256 or **HMAC-SHA-256 with a server-side pepper** for such tokens, avoiding roughly 300 ms of bcrypt latency per lookup ([WFP ADR 0008](https://docs.sso.earthobservation.vam.wfp.org/architecture/decisions/adrs/0008-api-key-hashing); [DEV, bcrypt to HMAC-SHA256](https://dev.to/vessel_api/the-946-millisecond-tax-migrating-api-key-auth-from-bcrypt-to-hmac-sha256-4c74)). No OWASP or NIST statement covers high-entropy tokens directly, so this rests on entropy reasoning. The invariant that keeps SHA-256 sound is that keys are **never user-chosen**; the moment a user can type a memorable secret, Argon2id becomes mandatory. A pepper from a `DICERI_*` variable is cheap optional hardening that makes a stolen database file useless even for offline candidate checks.

| Value | Example | Generation | Storage | May appear in URLs |
| --- | --- | --- | --- | --- |
| Identifier | `rooms.id`, `accounts.id`, `join_requests.id` | v7 in app, behind a port | 16-byte `BLOB` / `uuid` | Only where another credential gates access |
| Capability | room share code | 128 bits CSPRNG, base62 | `TEXT UNIQUE`, plaintext | Yes, that is its purpose |
| Secret | host key, account key | 128 bits CSPRNG | SHA-256 (or HMAC) `BLOB UNIQUE` | Never; cookie or header only |

Exposure of v7 ids follows from the same split. Join-request ids can appear in host-only URLs because the host key already gates them. Account ids reveal sign-up time, so they are returned only to their owner, if at all; the public handle is the `username`.

## UUIDv7 wins on standardization and locality, not raw speed

The performance case for time-ordered keys is real but scale-dependent. Random v4 keys scatter inserts across the B-tree; Buildkite reported a **50% reduction in WAL rate** on its primary database after moving new tables to v7, chose v7 over integers because integers "need coordination" when sharding, and called the 16-versus-8-byte overhead marginal ([Buildkite](https://buildkite.engineering/goodbye-integers-hello-uuids/)). Community PostgreSQL 18 benchmarks with uneven methodology point the same way: about 10x faster v7 inserts and a quarter smaller index at 100M rows ([dev.to/regyl](https://dev.to/regyl/postgresql-uuidv4-vs-uuidv7-1pdf)), up to 35% more space for v4 ([TigerData](https://www.tigerdata.com/blog/how-sequential-uuidv7-boosts-ingestion-performance)), and leaf density of 91% versus 58% ([dev.to/ahmet_gedik](https://dev.to/ahmet_gedik778845/how-uuid-v7-primary-keys-cut-b-tree-bloat-in-our-video-store-585n)). At small sizes the difference vanishes, and no SQLite-specific benchmark exists. For Diceri's volumes the stronger reasons are that v7 is the IETF standard, PostgreSQL 18 ships a native `uuidv7()` and `uuid_extract_timestamp()` ([PG 18 release notes](https://www.postgresql.org/docs/release/18.0/); [PG 18 UUID functions](https://www.postgresql.org/docs/18/functions-uuid.html)), and time order gives free, stable keyset pagination. ULID has the same layout idea but no version or variant bits, so it is not an RFC UUID ([ULID spec](https://github.com/ulid/spec)); Snowflake ids and database identities both need coordination a single app-side generator does not.

Generation belongs in the application, not the database. SQLite has no v7 function, app-side generation behaves the same on both engines, and the use case knows the id before the insert. `Uuid::now_v7()` guarantees ordering for ids "generated through this method by the same process" ([docs.rs uuid](https://docs.rs/uuid/latest/uuid/struct.Uuid.html)). Monotonicity is per generator only: PostgreSQL's `uuidv7()` is monotonic "within the same backend", not across backends ([brandur.org](https://brandur.org/fragments/uuid-v7-monotonicity)). A `DEFAULT uuidv7()` on PostgreSQL is a fine safety net, but the app still supplies the value. For tests, ids come through a port next to the existing `RandomSource`, whose fake builds ids from a fake clock, so ordering assertions stay deterministic.

Storage is settled by sqlx's own encoding. In `sqlx-sqlite` 0.9.1, `Uuid` encodes as a blob of `as_bytes()` and decodes only from blob bytes, while the `Hyphenated` and `Simple` wrappers use TEXT ([sqlx-sqlite 0.9.1 source](https://docs.rs/crate/sqlx-sqlite/latest/source/src/types/uuid.rs)). SQLite compares BLOBs with `memcmp()` and orders every TEXT value before every BLOB ([SQLite datatypes](https://www.sqlite.org/datatype3.html)), so v7 blobs sort by time and a stray TEXT id in the same column would both fail to decode and sort wrongly. RFC 9562 itself recommends the 128-bit binary form over the 288-bit text form ([RFC 9562 §6.13](https://www.rfc-editor.org/rfc/rfc9562.html)). The column is `id BLOB NOT NULL PRIMARY KEY CHECK (length(id) = 16)`; `STRICT` rejects TEXT, and the CHECK rejects wrong-sized blobs. On a rowid table a non-integer primary key is "really just a UNIQUE index", stored twice; `WITHOUT ROWID` stores one B-tree and helps small rows (under about 200 bytes on 4 KiB pages) keyed by non-integer or composite keys ([SQLite WITHOUT ROWID](https://www.sqlite.org/withoutrowid.html)), but SQLite advises measuring first. On PostgreSQL the column becomes `uuid` and the Rust type does not change ([sqlx Postgres types](https://docs.rs/sqlx/latest/sqlx/postgres/types/index.html)).

At the HTTP edge, ids are the canonical 36-character lowercase hyphenated form, which is what `Display`, serde and PostgreSQL output ([PG 18 uuid type](https://www.postgresql.org/docs/18/datatype-uuid.html)). Parsing accepts any case, as RFC 9562 §4 requires, but should reject non-v7 versions with a 404 rather than a 400, so responses do not teach callers about id structure. Rejecting non-v7 is a design choice, not a standard; Buildkite's experience that downstream validators break on version changes is the argument for being strict from day one.

In Rust, ids are newtypes in `domain` (`RoomId(Uuid)`, `AccountId(Uuid)`). That collides with a current rule: `apps/api/AGENTS.md` limits `diceri-domain` to `serde` and `thiserror`. `uuid` is pure and I/O-free when only used for parsing and building from given parts, so the clean fix is to add it to the allow-list in an ADR. The `sqlx::Type` impls belong in `infra` (private row structs, converted with `TryFrom`), so `domain` never sees sqlx. Today's `RoomId` type, which is really a share code, should be renamed so the name `RoomId` can mean the v7 key.

## The database is the last line of defense

Naming conventions matter mostly for consistency and for error mapping. The sources agree on lowercase snake_case, since PostgreSQL folds unquoted identifiers and mixed case forces quoting forever ([PostgreSQL wiki, Don't Do This](https://wiki.postgresql.org/wiki/Don't_Do_This)), and no authoritative source settles plural versus singular table names; Holywell prefers collective nouns but accepts plurals ([SQL Style Guide](https://www.sqlstyle.guide/)). Diceri's existing `accounts` table makes plural the rule. Holywell also argues against naming a key `id`, which conflicts with near-universal app practice; this report treats that as opinion and keeps `id` plus `<referenced_singular>_id`. For constraints and indexes, GitLab's scheme (`check_<table>_<column>_<kind>`, `fk_<table>_<column>_<ref>`, `index_<table>_on_<columns>`) exists precisely because services without an ORM need deterministic names, and PostgreSQL truncates identifiers at 63 characters ([GitLab constraint naming](https://docs.gitlab.com/development/database/constraint_naming_convention/)). Explicit names pay off on PostgreSQL, where sqlx's `DatabaseError::constraint()` reports them; on SQLite that accessor is empty, so portable adapters map errors with `is_unique_violation()`, `is_foreign_key_violation()` and `is_check_violation()` instead ([docs.rs sqlx DatabaseError](https://docs.rs/sqlx/latest/sqlx/error/trait.DatabaseError.html)).

Integrity rules are short. Every column is NOT NULL unless absence has a domain meaning. Every single-row invariant gets a CHECK that mirrors the domain newtype: for `Username`, `CHECK (length(username) BETWEEN 3 AND 20 AND username = lower(username))`, with the domain constructor remaining the primary validator. Text uses `TEXT` plus a length CHECK, never `varchar(n)` or `char(n)`, and money and durations are integers in named units ([PostgreSQL wiki](https://wiki.postgresql.org/wiki/Don't_Do_This)). Enums are `TEXT NOT NULL CHECK (status IN (...))`, which is portable and avoids PostgreSQL's hard-to-shrink native enums; a lookup table is warranted only when values are data or carry attributes. Foreign keys state `ON DELETE` explicitly (CASCADE for owned children, RESTRICT to block, SET NULL only for nullable weak links), because SQLite defaults to NO ACTION, and every child column gets an index, since "in most real systems, an index should be created on the child key columns" or parent deletes scan the child table ([SQLite foreign keys](https://www.sqlite.org/foreignkeys.html)). SQLite leaves foreign keys off per connection by default, but sqlx 0.9.1 turns them on ([docs.rs SqliteConnectOptions](https://docs.rs/sqlx/0.9.0/sqlx/sqlite/struct.SqliteConnectOptions.html)). `STRICT` tables keep every constraint working as usual and add `SQLITE_CONSTRAINT_DATATYPE` for values that cannot convert losslessly ([SQLite STRICT](https://www.sqlite.org/stricttables.html)).

Time has one representation per engine. `STRICT` has no DATETIME type, so SQLite instants are `INTEGER` Unix epoch in **milliseconds**, UTC, named `<participle>_at`; PostgreSQL uses `timestamptz`, never `timestamp`, and never `timestamptz(0)`, which rounds and can store a future time ([PostgreSQL wiki](https://wiki.postgresql.org/wiki/Don't_Do_This)). Milliseconds match the UUIDv7 timestamp and map losslessly onto `timestamptz`. The application sets business times; a DB default on `created_at` is a backstop, and `updated_at` is assigned in each UPDATE rather than by triggers, which are engine-specific. SQLite's `ALTER TABLE ADD COLUMN` also rejects parenthesized defaults like `(unixepoch())` ([SQLite ALTER TABLE](https://www.sqlite.org/lang_altertable.html)), another reason app-supplied times are the norm.

Deletion should be real. Brandur Leach reports never seeing a soft-deleted row actually restored in over ten years, while `deleted_at` predicates "bleed out into all parts of your code" and foreign keys stop protecting integrity; his alternative is to copy the row into a `deleted_records` table in the same transaction and hard-delete ([brandur.org](https://brandur.org/soft-deletion)), and thoughtbot reaches the same conclusion ([thoughtbot](https://thoughtbot.com/blog/the-hard-truth-about-soft-deletion)). For Diceri, where clones are deleted at call end, hard delete is also the privacy-correct default. A room that has ended is a domain state, not a deletion. Schemas normalize to 3NF, with no EAV tables and no CSV in TEXT; JSON is allowed only for opaque payloads read and written whole, stored as `TEXT CHECK (json_valid(col))` on SQLite and `jsonb` on PostgreSQL, and any field that is filtered, joined, sorted or unique gets promoted to a column.

## Versioned, forward-only migrations replace the startup CREATE TABLE

Before this work, `crates/infra/src/sqlite_accounts.rs` executed an inline `CREATE TABLE IF NOT EXISTS` at connect time, and the workspace pinned sqlx 0.9.1 with `default-features = false`, so `migrate` and `macros` were off. Moving to `sqlx::migrate!("./migrations")` requires enabling `migrate` (and `macros` for the macro itself), plus a `build.rs` with `cargo:rerun-if-changed=migrations` so new files trigger a rebuild. sqlx's guarantees make the policy nearly self-enforcing: each applied migration is checksummed, and an edited or deleted one fails startup with `VersionMismatch` or `VersionMissing`; reversible and simple migrations cannot be mixed; files starting with `-- no-transaction` run outside the per-migration transaction; and since 0.9.1 a misnamed `.sql` file is an error ([sqlx CHANGELOG](https://github.com/launchbadge/sqlx/blob/main/CHANGELOG.md); [launchbadge/sqlx](https://github.com/launchbadge/sqlx)).

The recommended policy is **forward-only**: no `.down.sql`, a rollback is a new migration, and applied migrations are never edited. Down migrations are rarely tested and destructive ones are dangerous, and sqlx forces a single choice anyway. Schema DDL and data backfills go in separate migrations, and large backfills run in batches from code. Any change an older running binary would break (rename, drop, type change, new NOT NULL) uses expand/contract across at least two releases: add the new shape alongside the old, deploy code that writes both and reads the new one, backfill, add the constraint, then drop the old shape later ([Xata, expand-contract](https://xata.io/glossary/expand-contract); [Encore, zero-downtime migration](https://encore.dev/articles/zero-downtime-migration)). On PostgreSQL, constraints are added `NOT VALID` and validated separately to take weaker locks ([PostgreSQL ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html)).

SQLite's `ALTER TABLE` is narrower: rename, add column, drop column; changing a type or adding CHECK, FK or UNIQUE requires the documented 12-step rebuild (foreign keys off, begin, create `new_X`, copy, drop, rename, recreate indexes and views, `foreign_key_check`, commit, foreign keys on), and renaming the old table first is explicitly called incorrect ([SQLite ALTER TABLE](https://www.sqlite.org/lang_altertable.html)). Because `PRAGMA foreign_keys` has no effect inside a transaction ([SQLite foreign keys](https://www.sqlite.org/foreignkeys.html)) and sqlx wraps each migration in one, rebuilds must be `-- no-transaction` migrations that manage `BEGIN`/`COMMIT` and the pragma themselves. When PostgreSQL arrives, migrations live in parallel per-engine directories numbered alike, since `STRICT` and `BLOB` have no PostgreSQL spelling; keeping DDL to `TEXT`, `INTEGER`, `BLOB`, CHECK, `ON CONFLICT ... DO UPDATE` and `RETURNING`, and avoiding `AUTOINCREMENT`, `INSERT OR REPLACE` and `GLOB`, keeps the two directories near-mechanical translations.

## SQLite holds up in production if writes stay single and short

SQLite "works great as the database engine for most low to medium traffic websites", and the documented reasons to leave it are data across a network, many concurrent writers, terabyte scale, or a site that "requires multiple servers" ([SQLite appropriate uses](https://www.sqlite.org/whentouse.html)). Diceri's durable data is small and single-host, so SQLite is the right engine today, and the triggers to move are concrete: a second API host (WAL cannot be shared across hosts), sustained `SQLITE_BUSY` or pool-acquire timeouts, or a need for PostgreSQL-only features.

WAL lets readers and the writer proceed concurrently, but there is still **exactly one writer at a time**; the WAL file is part of the persistent state; long-lived readers can starve checkpoints and grow it without bound; and WAL "does not work over a network filesystem" ([SQLite WAL](https://www.sqlite.org/wal.html)). The same page documents a rare WAL-reset corruption race in versions 3.7.0 through 3.51.2, fixed in 3.51.3; the bundled SQLite here is 3.54.1, so it is safe, but the floor is worth a rule because a dependency downgrade could reintroduce it. sqlx 0.9 sets foreign keys on and a 5 s busy timeout, but leaves journal mode unset and `synchronous` at SQLite's default FULL ([docs.rs SqliteConnectOptions](https://docs.rs/sqlx/0.9.0/sqlx/sqlite/struct.SqliteConnectOptions.html)). Community guidance favours `synchronous=NORMAL` in WAL mode ([OneUptime](https://oneuptime.com/blog/post/2026-02-02-sqlite-production-setup/view)), which never corrupts the database but can roll back the last commits on power loss. For Diceri, **FULL is the better choice for now**: writes are rare sign-ups, and a sign-up lost after the key was shown to the user would leave them holding a key that matches nothing. The rule is that the choice is explicit in code, not inherited.

Write contention is managed by discipline. Transactions that read and then write should start with `BEGIN IMMEDIATE`, because a deferred transaction that upgrades to a write can fail with `SQLITE_BUSY` without the busy timeout helping; this is standard SQLite practice but was not verified against a primary source in this research. Transactions stay short and never span a network or provider call. Index every predicate and sort, check hot queries with `EXPLAIN QUERY PLAN`, never query inside a loop over rows, and paginate with keysets on `(created_at, id)` because OFFSET reads and discards every skipped row and duplicates rows under concurrent inserts ([use-the-index-luke](https://use-the-index-luke.com/no-offset)).

Backups need two mechanisms. `VACUUM INTO` produces "a consistent snapshot" of a live database without blocking writers, leaves no traces of deleted content, and its target must not already exist ([SQLite VACUUM](https://www.sqlite.org/lang_vacuum.html)): it is the right tool before risky migrations and for periodic copies, written to a temp name, checked with `PRAGMA integrity_check`, then renamed. Continuous replication can come from Litestream, which streams changes to object storage as a separate process with no code changes; v0.5.18 is current ([litestream.io](https://litestream.io/); [Litestream releases](https://github.com/benbjohnson/litestream/releases)). Its license and point-in-time-restore details were not verified here. Copying the `.db` file alone while it is in use is never a backup, since recent commits live in `-wal`. A backup that has never been restored is a hope, so a scheduled restore drill records the observed recovery point and time.

## Ports keep sqlx out; contract tests keep fakes honest

No canonical Rust pattern exists, but practitioner consensus fits Diceri's existing layout: one aggregate-scoped trait per aggregate in `application::ports`, taking and returning domain types and a `thiserror` error enum, with intention-revealing methods rather than generic CRUD ([howtocodeit, hexagonal Rust](https://l-lin.github.io/programming-languages/rust/master-hexagonal-architecture-in-Rust)). The weak point everyone names is cross-repository transactions. Threading an sqlx `Transaction` through services leaks adapter details upward; the cleaner answer is first to ask whether the two tables are really one aggregate, and otherwise to add a unit-of-work port whose sqlx implementation owns the transaction ([DEV, hexagonal transactions](https://dev.to/2nguyenlong000k/handling-transactions-without-breaking-service-adapter-decoupling-in-hexagonal-architecture-with-golang-5ce1)). Adapters read rows into private structs and convert through domain constructors, so a corrupt row surfaces as a typed storage error rather than a panic.

sqlx 0.9 added a structural guard against injection: the `query*()` family accepts only `&'static str` by default, and anything else must be wrapped in `AssertSqlSafe(..)` ([sqlx 0.9.0 release](https://github.com/launchbadge/sqlx/discussions/4271)). That makes `AssertSqlSafe` the SQL equivalent of `unsafe`: allowed only in `infra`, for allow-listed identifiers, with a justifying comment, consistent with OWASP's rule that values are bound and structure (table names, sort direction) is allow-listed ([OWASP SQL Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)). Compile-time `query!` macros are a reasonable later step, but they need committed `.sqlx/` offline data and a `cargo sqlx prepare --check` gate, and SQLite nullability inference is "fragile" around `LEFT JOIN`s ([docs.rs query!](https://docs.rs/sqlx/0.9.0/sqlx/macro.query.html)).

Testing has three layers. Use-case tests use in-memory fakes. A single contract suite per port runs against both the fake and the real adapter, so the in-memory and SQLite account stores cannot drift on uniqueness, ordering or not-found semantics. Adapter tests build every database by running the real migrations ([docs.rs sqlx::test](https://docs.rs/sqlx/0.9.0/sqlx/attr.test.html)). Data-transforming migrations get a test that seeds the old shape and asserts the new one, and CI runs `PRAGMA integrity_check` and `foreign_key_check` after applying everything from empty. PostgreSQL tests, when they come, need a real server and belong in `just ci`, not in the network-free `just test`.

## Privacy turns retention into a schema property

Both GDPR and LGPD reach Diceri's small schema. Usernames, account ids and key hashes linked to them are personal data (hashes are pseudonymous, not anonymous). IP addresses are online identifiers under GDPR Recital 30 ([Recital 30](https://gdpr-info.eu/recitals/no-30/)), and the CJEU's *Breyer* ruling holds that even a dynamic IP is personal data for an operator with legal means to identify the user ([CJEU](https://curia.europa.eu/jcms/jcms/p1_236867/cs)). GDPR Article 5 requires minimization, storage limitation and demonstrable accountability ([GDPR Art. 5](https://gdpr-info.eu/art-5-gdpr/)); LGPD lists biometric data as sensitive (Art. 5 II), limits processing to the minimum necessary (Art. 6 III), requires deletion once processing ends (Art. 16), a record of processing operations (Art. 37) and incident notification (Art. 48) ([Lei 13.709](https://www.planalto.gov.br/ccivil_03/_ato2015-2018/2018/lei/l13709.htm)), and ANPD Resolution 15/2024 sets **3 business days** for notifying the authority and data subjects ([Resolução 15/2024](https://sintse.tse.jus.br/documentos/2024/Abr/26/diario-oficial-da-uniao-secao-1/autoridade-nacional-de-protecao-de-dados-resolucao-no-15-de-24-de-abril-de-2024-aprova-o-regulamento)). Voice samples and clone embeddings are biometric under LGPD and likely under GDPR Article 9 (not fetched here).

The schema consequences are direct. No column ever holds audio, transcripts, translations or voice embeddings, which extends [ADR 0007](../../decisions/0007-transcripts-stay-in-the-browser.md) and [ADR 0006](../../decisions/0006-voice-cloning-consent.md) into a review rule. Raw IPs stay in the in-memory rate limiter; if abuse handling ever needs persistence, store a truncated or keyed hash with a short TTL. Every table with personal data has a documented purpose, legal basis and retention, a deletion path, and account erasure is proven by a test that no referencing row survives. Deleted data lingers in SQLite free pages, the WAL and backups: `VACUUM` removes "all traces of deleted content" and is the alternative to `PRAGMA secure_delete` ([SQLite VACUUM](https://www.sqlite.org/lang_vacuum.html)), and backup retention must be bounded so erased rows age out within a window the privacy notice states. A short data inventory in `docs/` (table, field, purpose, basis, retention) doubles as the LGPD Art. 37 and GDPR Art. 30 record.

Operationally, the database file, `-wal` and `-shm` live in a dedicated 0700 directory owned by the service user, outside any web-served path, with encryption at rest from the volume. On PostgreSQL the app gets a DML-only role, separate from the migration owner, over TLS, following OWASP's "do not assign DBA or admin type access" ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)). Tracing records repository operation names and durations, never bound values, usernames, keys or hashes.

## Conclusion

The most consequential finding is that "use UUIDv7 for ids" is only safe as half of a pair of rules: the other half is that nothing granting access is ever a UUIDv7. Diceri already had the right instincts (128-bit base62 codes, hashed keys), so the risk is not ignorance but drift: a future contributor "simplifying" the room link into the primary key. Writing the three-value distinction into AGENTS.md, and renaming the old `RoomId` to a share-code type, closes that door structurally rather than by memory.

The second insight is about timing. Every expensive change in this report (v7 keys for accounts, millisecond timestamps, migrations replacing the inline schema, the `uuid` dependency in `domain`) is cheap now because `accounts` is the only durable table and has a handful of rows. Each further table adopted under the old conventions multiplies the 12-step rebuilds needed later.

## Proposed AGENTS.md rules

The adopted, project-specific version of these rules is [`AGENTS.md`](../../../AGENTS.md) §14.

**Identifiers, capabilities and secrets**

1. Every table's primary key is `id`, a UUIDv7 generated in the application behind an id port, never by the database.
2. Never use a UUID (any version) as a capability or secret; RFC 9562 §8 forbids it.
3. Room share links are a separate value: 128 CSPRNG bits as 22 base62 chars, `UNIQUE`, never derived from `id`.
4. Host keys, account keys and other bearer secrets are 128-bit CSPRNG values, stored only as SHA-256 (or HMAC-SHA-256 with a `DICERI_*` pepper), never in plaintext, never user-chosen; a user-chosen secret requires Argon2id.
5. Expose v7 ids in URLs only where another credential already gates access; never expose account ids publicly.
6. Ids are domain newtypes (`RoomId(Uuid)`); `uuid` is the only id dependency in `domain`; sqlx impls live in `infra`.
7. JSON and paths use the lowercase hyphenated form; parse case-insensitively, reject non-v7 with 404.

**Schema**

8. SQLite: every `CREATE TABLE` ends with `STRICT`; UUIDs are `BLOB NOT NULL CHECK (length(col) = 16)`; PostgreSQL uses `uuid`.
9. Names are lowercase snake_case; tables plural; foreign keys `<referenced_singular>_id`; booleans `is_`/`has_`; units in names (`_ms`, `_bytes`); no reserved words.
10. Name every constraint and index: `check_<table>_<col>_<kind>`, `fk_<table>_<col>_<ref>`, `uq_<table>_<cols>`, `index_<table>_on_<cols>`.
11. Columns are `NOT NULL` unless absence has a documented domain meaning.
12. Every single-row invariant of a domain type gets a `CHECK` mirroring it; use `TEXT` + CHECK, never `varchar(n)`/`char(n)`.
13. Enums are `TEXT NOT NULL CHECK (col IN (...))`; no native PostgreSQL enums.
14. Every foreign key states `ON DELETE` explicitly and its child column is indexed.
15. Instants are UTC: SQLite `INTEGER` Unix milliseconds named `<participle>_at`; PostgreSQL `timestamptz`; the app sets them; DB defaults are only a backstop; no triggers for `updated_at`.
16. Hard delete by default; model "ended" or "closed" as a state column; no `deleted_at` soft delete without an ADR.
17. Normalize to 3NF; no EAV, no lists in TEXT; JSON only for opaque whole-read payloads, never for queried fields.

**Migrations**

18. All schema changes are `sqlx::migrate!()` files in `crates/infra/migrations/`, named `<YYYYMMDDHHMMSS>_<snake_description>.sql`, applied at startup before serving.
19. Migrations are forward-only: no `.down.sql`; never edit or delete a merged migration; fix forward with a new one.
20. One logical change per migration; DDL and data backfills are separate migrations; large backfills run in batches from code.
21. Changes that break the previous release (rename, drop, type change, new NOT NULL) use expand/contract across at least two releases.
22. SQLite table rebuilds follow the official 12-step procedure in a `-- no-transaction` migration.
23. Write portable SQL: `ON CONFLICT ... DO UPDATE` and `RETURNING` are fine; no `AUTOINCREMENT`, `INSERT OR REPLACE`, `GLOB` or engine functions in queries.

**Data access**

24. Port traits in `application::ports` use domain types and a `thiserror` error enum only; never `sqlx`, `Row`, `Pool` or `Transaction`.
25. Port methods are aggregate-scoped and intention-revealing; add one only when a use case needs it.
26. Map driver errors with `is_unique_violation()`/`is_foreign_key_violation()`/`is_check_violation()`, not message or SQLSTATE parsing.
27. Decode rows into private structs, then into domain types via their constructors; never derive `FromRow` on domain types.
28. Bind every value; SQL text is `&'static str`; `AssertSqlSafe` only in `infra`, for allow-listed identifiers, with a justifying comment.
29. Cross-aggregate atomicity goes through a unit-of-work port implemented in `infra`; never thread a transaction through `application`.
30. Every new query ships with its index or a note naming the index that covers it; no queries inside loops; list endpoints use keyset pagination on `(created_at, id)`, never OFFSET.

**SQLite operation**

31. Set all connection options explicitly in one place: WAL, `foreign_keys(true)`, `busy_timeout` 5 s, `synchronous` FULL (change only with a written reason), `optimize_on_close`.
32. Read-then-write transactions use `BEGIN IMMEDIATE` (or a one-connection write pool); transactions never span network or provider calls.
33. Keep the database on local disk only, in a 0700 directory owned by the service user (file 0600), outside any served path; bundled SQLite must be 3.51.3 or later.
34. Back up with `VACUUM INTO` snapshots checked with `PRAGMA integrity_check` (plus continuous replication when available); never copy a live `.db` without its WAL; restore-drill on a schedule.

**Testing**

35. Every repository port has one contract test suite run against both its in-memory fake and its SQL adapter.
36. Adapter tests build databases by running the real migrations; every data migration has a before/after test; CI applies all migrations from empty and runs `integrity_check` and `foreign_key_check`.

**Privacy and security**

37. No table or column may store audio, transcripts, translations or voice embeddings.
38. Never persist raw IP addresses; keep them in memory, or store a truncated or keyed hash with a short TTL.
39. Every table holding personal data has a documented purpose, legal basis and retention in the data inventory, plus a tested deletion path; account erasure must leave no referencing row.
40. Erased data must also leave free pages and backups: periodic `VACUUM` (or `secure_delete`) and a bounded backup retention.
41. Never log bound parameters, usernames, keys, hashes or the database URL; log operation names, ids and durations only.
42. PostgreSQL (later): the app connects with a DML-only role separate from the migration owner, over TLS.
