# Inworld's voice cap counts stored clones, not creations

Inworld's per-plan "custom voices" number (**On-Demand 100, Creator 500, Builder 3,000, Developer 10,000, Growth 30,000**) caps how many instant clones, designed voices and copied voices an organization **holds at the same time**. It is not a monthly or lifetime creation counter, and deleting a private voice frees its slot immediately. Diceri confirmed this first-hand on 2026-11-27: capacity read 0/100, two clones were created and deleted, and capacity returned to 0 at once. No official page mentions a monthly creation cap or a per-clone fee, so Inworld fits Diceri's create-on-join/delete-on-leave model, which ElevenLabs' 95-operation monthly limit broke. The limits that do bind are two others. The first is a **clone-creation rate limit**: Inworld's TTS billing page publishes **2 / 3 / 5 / 10 / 20 requests per minute** by plan, although the pricing page, the cloning guide and the rate-limits page give no figure. The second is **concurrent TTS generations**: **5 / 10 / 50 / 150 / 500** by plan, per account and shared across keys. Cloning works only through a stored voice. There is no inline reference audio per request, so every participant goes through a create → synthesize → delete cycle. That cycle measured **3.3–4.3 s to clone** and **about 230 ms to first audio** from the production host, including a Portuguese clone speaking Japanese. The weakest part is legal and data handling. Cloning samples are **excluded from Zero Data Retention** (ZDR), which itself requires the $300 Developer plan. Data stays in the US outside Enterprise, the DPA has no LGPD clause, and no document says when reference audio is purged after a delete. The recommendation is **Creator for the evaluation and a consenting-tester beta, and Developer for public launch**, with a rate-limited clone queue, typed handling of 429 and 400 errors, a capacity check plus a leak sweeper, and nine written questions to Inworld before production traffic flows.

## One stock cap, two flow limits: what each Inworld number means

Inworld documents the custom-voice allowance as a stock of voices that exist at one time. The instant-cloning guide says "your plan sets how many custom voices your organization can have", and that instant clones, designed voices and voices copied in with a copy token "all count toward one limit". Professional voice clones are excluded because "they have their own voice slots" ([Instant voice cloning](https://docs.inworld.ai/tts/instant-voice-cloning.md)). A free capacity endpoint, `GET /voices/v1/voices:customVoiceCapacity`, returns `usedCustomVoices`, defined as "how many custom voices your organization has now, across all its workspaces", and `maxCustomVoices`, defined as "your plan's limit plus any add-ons". No billing period or reset appears in either the guide or the API reference ([Get custom voice capacity](https://docs.inworld.ai/api-reference/voiceAPI/voiceservice/get-custom-voice-capacity.md)). Deletion is explicit: "delete private voices you no longer use, which frees room right away" ([Instant voice cloning](https://docs.inworld.ai/tts/instant-voice-cloning.md)). The one exception is a voice shared to the Voice Library. Such a voice cannot be deleted until it is removed from the library, and **removal has a 2-year notice period** ([Voice Library Addendum](https://inworld.ai/voice-library-addendum)). Diceri must never share a participant clone there.

The fields describe a stock, but Diceri did not rely on wording alone. The [measured probe](notes/measured-probe.md) ran from the production host with Diceri's own On-Demand key and a synthetic fixture voice. Capacity read `{"usedCustomVoices":0,"maxCustomVoices":100}` before the test. Two clones were then created and deleted, each delete returned HTTP 200, and capacity was **back to 0 immediately afterwards**. No official page fetched mentions a monthly creation cap, an edit cap, a per-clone fee or any cost for cloning. The billing page charges per request only for voice-design prompts sent with a synthesis request ([TTS billing](https://docs.inworld.ai/tts/resources/billing)). That is an absence of evidence, not a promise, and it heads the questions for Inworld below. Search-engine snippets show an older, much smaller allowance (5 / 50 / 700 / 1,000). The live [pricing page](https://inworld.ai/pricing) and [founder pricing page](https://inworld.ai/founder-pricing) no longer carry it, and the change could not be dated.

Two scoping details matter operationally. The cap is **per organization and shared by every workspace**. The voice-list endpoint, by contrast, covers only the API key's workspace, so its count can be lower than `usedCustomVoices` ([Instant voice cloning](https://docs.inworld.ai/tts/instant-voice-cloning.md)). Rate and concurrency limits "apply per account and are shared across your API keys" ([Rate limits](https://docs.inworld.ai/resources/rate-limits)). A staging workspace or the end-to-end suite running under the production account therefore spends production's clone rate and concurrency. That is the same failure the recent commit keeping end-to-end runs off the clone quota had to work around for ElevenLabs.

## The clone-rate figure exists on one page and nowhere else

The two research notes disagree because they read different pages. The quota note cites the TTS billing page, which has a row "Voice cloning API (requests/min)" with values **2 / 3 / 5 / 10 / 20 / Custom** for On-Demand through Enterprise, and an identical row for the voice design API ([TTS billing](https://docs.inworld.ai/tts/resources/billing)). The API-and-limits note read the pricing page, the cloning guide, the rate-limits page and the concurrency page. It concluded that "no number is published". On those four pages that is true. The cloning guide says only that "voice cloning has lower rate limits than regular speech synthesis" ([Instant voice cloning](https://docs.inworld.ai/tts/instant-voice-cloning.md)). The rate-limits page lists "voice design and cloning limits" as a category and defers the numbers to pricing ([Rate limits](https://docs.inworld.ai/resources/rate-limits)). The pricing page shows no cloning rate ([Pricing](https://inworld.ai/pricing)). A third data point is unverified. A search snippet attributed a single "Voice cloning API requests/min 5" row to the founder-pricing page, but the fetched page does not show it, and the plan it belonged to is unclear ([Founder pricing](https://inworld.ai/founder-pricing)). Five matches Builder in the billing table, which is consistent with the snippet being an older render of the same per-plan data.

The reconciliation is that a per-plan figure **is published, on one official docs page**, and the other official pages are silent rather than contradictory. The billing table gains credibility because its concurrency and WebSocket rows match the dedicated [concurrency page](https://docs.inworld.ai/resources/concurrency-limits) exactly. Diceri should design to the billing-page numbers as the documented contract and get written confirmation, because one page is thin evidence for a limit that decides launch capacity. The probe could not settle the question. It made only two clones, which is within even On-Demand's 2 per minute. No page says whether a clone-rate rejection is a 429 or whether it carries `Retry-After`. The general rule is that per-second limits return 429 with no `Retry-After`, and per-minute limits "may" include one ([Rate limits](https://docs.inworld.ai/resources/rate-limits)). No rate limit is documented for list, delete or capacity calls, and no per-day cloning limit is documented either.

For Diceri, the rate is the real constraint and the stock is not. Two clones a minute is 120 an hour, which covers "thousands of joins a month" on volume. It does not cover a burst: ten people opening the lobby in the same minute would wait up to five minutes on On-Demand. Developer's 10 per minute absorbs ordinary bursts. Growth's 20 per minute is the first tier where a 20-person webinar start clears in one minute.

## Instant cloning is a stored-voice API: create, synthesize, delete

Creation is `POST https://api.inworld.ai/voices/v1/voices:clone` with Basic auth and a key that has write access to voices. A key without it gets error code 7. The JSON body takes a required `displayName` and `voiceSamples[]` of base64 WAV or MP3, an optional `transcription` (generated automatically, and ignored by TTS-2), and either `languageCode` (`pt-BR`) or the legacy `langCode` (`PT_BR`, `AUTO`). It also takes `audioProcessingConfig.removeBackgroundNoise`, which "may degrade already-clean audio". The response synchronously returns `voice.voiceId` in the form `{workspace}__{voice}`, with `source: IVC` and a `languageCode` that **cannot be changed after creation** ([Clone a voice](https://docs.inworld.ai/api-reference/voiceAPI/voiceservice/clone-voice)). Guidance is "10–30 sec", with clips cut at 30 s, and Inworld states a minimum of **3 seconds** ([Voice cloning guide](https://docs.inworld.ai/tts/voice-cloning)). No sample rate or bit depth is specified, no readiness or polling contract exists for instant clones (only professional clones train asynchronously), and the API has **no consent or attestation field**.

The probe filled the gaps the docs leave. A 5.84 s clip cloned with HTTP 200 in **4,320 ms at 24 kHz** and **3,335 ms at 16 kHz mono 16-bit**, which is Diceri's kept recording format ([measured probe](notes/measured-probe.md)). The voice was usable on the very next request, with no polling. Several seconds is too long to add to the moment someone clicks "join", so the clone call belongs in the pre-join step, overlapping the time the person spends in the lobby. The probe's clip was shorter than Inworld's recommended 10 s, so Diceri's ~10 s recordings sit at the bottom of the recommended window, not below it.

Inline reference audio does not exist. The HTTP stream request accepts "either `voiceId` or `voiceDesign`, not both", where `voiceDesign` is a text prompt, and the WebSocket `create` message requires a `voiceId` ([Stream API](https://docs.inworld.ai/api-reference/ttsAPI/texttospeech/synthesize-speech-stream), [WebSocket API](https://docs.inworld.ai/api-reference/ttsAPI/texttospeech/synthesize-speech-websocket)). Inworld's "zero-shot" means no training step, not audio sent per request. This maps one-to-one onto Diceri's existing `VoiceCloner` create/delete port. Cleanup is `DELETE /voices/v1/voices/{voiceId}`, which returns `{}`. Leaks can be found with `GET /voices/v1/voices?filter=source="IVC"`, ordered by `created_at`, with `pageSize` up to 2,000. Pagination is offset-based with no stable snapshot, so a sweeper must deduplicate on `voiceId` ([List voices](https://docs.inworld.ai/api-reference/voiceAPI/voiceservice/list-voices)).

Cross-lingual use is built in. A voice "delivers the best speaker similarity when it speaks the language it was cloned in". In any other language, the model "makes a best-effort attempt to speak the target language natively, without carrying over the accent". Keeping the accent requires explicit steering on `inworld-tts-2` only. The 15 Tier 1 languages are ar, zh, nl, en, fr, de, he, hi, it, ja, ko, pl, pt, ru and es. A further 79 Tier 2 languages "can vary more", and 376 Tier 3 languages are unevaluated ([Multilingual](https://docs.inworld.ai/tts/capabilities/multilingual)). In the probe, the pt-BR clone spoke a Japanese sentence with **first audio at 223 ms** against 238 ms for Portuguese ([measured probe](notes/measured-probe.md)). That proves the path works and costs nothing in latency. Nobody listened, so similarity and pronunciation remain for the blind evaluation the earlier provider research planned. Diceri should set `languageCode` at clone time to the speaker's lobby language, because a short clip can be misdetected and the value is immutable. It should also send `language` on every synthesis, since short translated turns are exactly the inputs auto-detection gets wrong.

Streaming comes in two transports. HTTP NDJSON (`POST /tts/v1/voice:stream`) takes up to 4,000 UTF-16 units, and "errors can arrive mid-stream after an HTTP 200". The bidirectional WebSocket (`wss://api.inworld.ai/tts/v1/voice:streamBidirectional`) carries many contexts per connection, takes up to 2,000 units per message, offers `cancel_context` for barge-in, and closes after 10 minutes of inactivity. Headerless `PCM` runs at 8–48 kHz ([Stream API](https://docs.inworld.ai/api-reference/ttsAPI/texttospeech/synthesize-speech-stream), [WebSocket API](https://docs.inworld.ai/api-reference/ttsAPI/texttospeech/synthesize-speech-websocket)). Inworld quotes server-side P90 time to first byte of 100 ms for `inworld-tts-2` and 20 ms for Flash ([TTS models](https://docs.inworld.ai/tts/tts-models)). The probe's ~230 ms end to end from Diceri's host is consistent with that plus network.

## Concurrency, not voice slots, sets how many calls run at once

Each in-flight HTTP request counts as one generation, and so does each **active** WebSocket context. Idle contexts stop counting, and a closed context frees its slot once its audio is delivered. Over the limit, HTTP returns 429, and the WebSocket returns `code: 8` (ResourceExhausted) on `create_context` or on the first message that wakes an idle context. Messages sent after that point may be dropped. Requests above the guaranteed figure are "best-effort based on available capacity", and Inworld says a customer "can typically handle at least 4x your concurrent generation limit in simultaneous conversations" ([Concurrency limits](https://docs.inworld.ai/resources/concurrency-limits)). In a two-person call people mostly take turns, so a call holds about one active generation and sometimes two. On-Demand's 5 therefore guarantees only a handful of simultaneous calls, Creator's 10 a few more, and Builder's 50 is the first tier that is comfortable for a public launch with dozens of concurrent calls. Measured against these figures, the voice stock never binds: Creator holds 500 voices but can guarantee speech for only about 10–20 active speakers.

## Inworld keeps the samples, and the contract has LGPD gaps

The data terms are where Inworld is weakest for Diceri. ZDR is available only on **Developer, Growth and Enterprise**. On-Demand, Creator and Builder can see the setting but cannot change it. ZDR redacts TTS input text and output from logs. However, "voice cloning audio samples and Voice Design descriptions" **are not eligible**: Inworld keeps "the initial source audio required to build the voice itself" ([ZDR](https://docs.inworld.ai/tts/zero-data-retention), [Security](https://inworld.ai/security)). No page states the default retention for TTS text and audio on non-ZDR plans. That matters because the text Diceri sends is a translated transcript of the call, which Diceri's own rules forbid logging. Enabling ZDR also "does not delete content already collected".

Training and retention terms do not agree with each other. ToS §4 promises "No Training" on non-public Materials, but it licenses them "to operate, maintain, and improve the Services" ([Terms](https://inworld.ai/terms)). Service Specific Terms §1(d) grants use of Input "to improve the Services" ([Service Specific Terms](https://inworld.ai/service-specific-terms)). The Privacy Notice uses voice recordings to "derive a digital model of speech characteristics" and to improve services "(unless you opt out)". It keeps biometric data "for up to three years", in a sentence that looks truncated in extraction ([Privacy](https://inworld.ai/privacy)). The delete endpoint is described only as removing the voice from the workspace. **Nothing says when the reference audio or derived embeddings are purged** ([Delete voice](https://docs.inworld.ai/api-reference/voiceAPI/voiceservice/delete-voice.md)). Diceri can therefore meet ADR 0006's "clones are deleted when the call ends" at the API level, but it cannot yet show that the underlying samples are gone.

Consent sits entirely with the customer. The Portal has a "Confirm you have the rights to clone the voice" checkbox, and the API has nothing equivalent ([Voice cloning guide](https://docs.inworld.ai/tts/voice-cloning)). Clones may use "your voice or a voice you are authorized to share", and the customer warrants all rights in its Input ([Service Specific Terms](https://inworld.ai/service-specific-terms)). The AUP forbids impersonation without consent and requires that users be told "clearly and prominently" that they are hearing AI ([AUP](https://inworld.ai/aup)). Diceri's per-call opt-in already supplies the consent. It should also keep a consent record (who, when, which call, scope), because Diceri indemnifies Inworld (ToS §11), and it should label translated voices as synthetic. No watermarking is documented.

The public DPA makes Inworld a processor, covers EEA and UK transfers with SCCs, and applies to anyone "using the Services". The pricing page, however, lists "SLA & DPA" only under Enterprise. The DPA has **no LGPD or ANPD clauses**, its subprocessor list sits behind a JavaScript-rendered trust center, and data is processed **in the US by default**, with EU and India regions Enterprise-only ([DPA](https://inworld.ai/data-processing-addendum), [Security](https://inworld.ai/security)). For Brazilian users, LGPD Art. 33 then needs a basis other than ANPD standard clauses. That is a legal reading for counsel, not a verified conclusion. Finally, the ToS licence is "solely for your internal business purposes" and non-sublicensable ([Terms](https://inworld.ai/terms)). Serving translated speech to call participants is ordinary API use, but the wording should be confirmed for a public product.

## Fit, plan and the handling the app must build

Inworld fits create-on-join/delete-on-leave. The stock cap only bounds how many participants hold a clone at once, deletion frees slots instantly (documented and measured), and no creation quota or clone fee is documented. The design risks are a low and thinly documented clone rate, tight concurrency on the cheap tiers, and data terms that need written fixes. **Creator ($25)** is the right plan for the blind evaluation and a beta with consenting testers: 3 clones per minute and 10 generations are enough, and it is the cheapest tier above the free one. **Developer ($300)** is the plan for public launch. It is the first tier with ZDR, which keeps call transcripts out of Inworld's logs. Its 10 clones per minute absorb join bursts, and its 150 generations guarantee far more simultaneous calls than launch traffic needs. Builder ($100) is the fallback only if Inworld confirms in writing that non-ZDR plans neither log TTS text beyond a short window nor use it for improvement.

The app must handle the limits in the following ways. Creation must not depend on Inworld's documentation being right.

| Situation | Signal | Diceri behaviour |
|---|---|---|
| Join burst | none (client-side) | Serialize clone calls through one per-account token bucket set to the plan's rpm, started at pre-join so the 3–4 s clone overlaps the lobby. |
| Clone rate exceeded | 429, `Retry-After` maybe | Honour `Retry-After`. Otherwise use exponential backoff with jitter (1 s base, 30 s cap, about 5 tries, per [Rate limits](https://docs.inworld.ai/resources/rate-limits)). If the clone is not ready when the call starts, the speaker gets the captions-only fallback (ADR 0014) until it is, never a blocked join. |
| Voice cap reached | 400 `INVALID_ARGUMENT`, "exceeded your plan's maximum number of custom voices" | Not retryable. Distinguish it from bad audio (also 400) by reading `voices:customVoiceCapacity`, then run the sweeper and fall back to captions. Alert when usage passes 80%. |
| Leaked clones | used count above live cloned participants | Periodic sweeper: list `source="IVC"` by `created_at`, deduplicate on `voiceId`, and delete any clone not tied to a live call. Delete on call end with retries. |
| TTS concurrency | HTTP 429; WebSocket `code: 8` | Close idle contexts promptly, use one WebSocket per agent worker with one context per (speaker, listener language), back off and retry the utterance, and alert on sustained 429s before upgrading. |
| Mid-stream failure | error object after HTTP 200 | Treat it as an utterance failure and resynthesize once. Never assume a 200 is complete. |
| Shared limits | per account, org-wide cap | Run staging and end-to-end tests under a **separate Inworld organization and account**, not just a separate workspace or key. |

Open these questions with Inworld in writing before production traffic:

| # | Question | Why it matters |
|---|---|---|
| 1 | Is the per-plan clone rate on the billing page (2/3/5/10/20 rpm) current, and is a clone-rate rejection a 429 with `Retry-After`? | Sets queue size and plan choice. |
| 2 | Is there any daily, monthly or fair-use limit on create/delete churn, and is instant cloning free of charge on every plan? | The ElevenLabs failure mode. |

| 5 | What is the default retention for TTS input text and output on non-ZDR plans, and which models does ZDR cover (TTS-2 and Flash)? | Decides Builder vs Developer. |
| 6 | Does the public DPA apply on self-serve plans, and will Inworld sign ANPD standard clauses for Brazilian data? | LGPD Art. 33 transfer basis. |
| 7 | Who are the subprocessors, and where are voices hosted? | Trust center unreadable; data inventory needs it. |
| 8 | Does "internal business purposes" permit serving output to a public product's end users? | Licence scope. |
| 9 | What latency and similarity should we expect from a ~10 s 16 kHz browser clip, and does `inworld-tts-2-flash` support the same clones cross-lingually? | Evaluation design; possible cost lever. |

## Conclusion

The question that broke ElevenLabs, "how many voices may we create?", has a reassuring answer at Inworld: it counts voices held, not voices made, and the probe watched a deleted slot come back. The risk has moved, not disappeared. It now sits in a per-minute clone rate that only one official page states, and in concurrency figures that make the free and $25 tiers suitable for testing but not for launch. Treat both as contracts to verify, and build the queue, the 429 handling and the captions fallback as though they will be hit.

The less obvious finding is that Inworld's privacy story is weaker than the earlier provider comparison assumed. ZDR exists, but it costs $300 a month, never covers the voice samples themselves, and the documents disagree on improvement use and purge timing. For Diceri the deciding conversation is therefore with Inworld's legal and sales team, not the API. Answers to questions 3 to 6 determine whether Developer is enough or whether Brazilian and EU users push the company toward Enterprise regional terms, which would change the cost comparison against Voxtral's store-nothing design.
